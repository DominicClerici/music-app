# Caveats — Deviations from the Pinned Design

The design docs (`ROADMAP.md`, `PHASE_1.md`–`PHASE_8.md`) are binding, but implementation will occasionally force a deviation. Every deviation is logged here so its impact stays visible to later sessions, which otherwise have no memory of it.

**Log an entry when:** a pinned contract/algorithm/data format is changed or reinterpreted; a printed worked-example sample is found wrong (golden-value arbitration rule 2, `ROADMAP.md` §3); an algorithm ambiguity is resolved; scope is moved between phases/sessions; a dependency pin forces a design adjustment.

**Not caveats:** bugs fixed in this project's own new code, refactors that don't change pinned contracts, or decisions the PHASE docs explicitly left open (those are just decisions — record them in the session plan and PROGRESS.md).

## Entry format

```
### C-<nn>: <one-line title>
- **Date / session:** YYYY-MM-DD, session NN (Phase N)
- **What deviated:** the pinned text vs. what was actually built
- **Why:** the concrete forcing reason
- **Impact:** downstream PHASE docs / phases / fixtures affected; what a later session must know
- **Doc amendment:** commit hash of the PHASE/ROADMAP amendment, or "none needed" with justification
- **Status:** open | resolved
```

Numbered sequentially (`C-01`, `C-02`, …), never renumbered. If a later session resolves or supersedes an entry, update its **Status** in place and note how — do not delete entries.

### C-07: §3.3 retargeting — three under-specified points resolved (guide3-over-sus, guide7 fallback scope, <60-tick drop on all retrigger segments)
- **Date / session:** 2026-07-16, session 06 (Phase 5, chunk 1), T3 foundations
- **What deviated:** PHASE_5 §3.3's degree table + `onChordChange` prose left three points under-specified; `parts/retarget.py` resolves them as: **(a)** `guide3` over a **suspended** chord (which has no guide third) → the `third` slot (the suspension tone); §3.3's `guide3` fallback cell is "—", implicitly assuming a third always exists. **(b)** `guide7` fallback broadened from the literal "triads → the fifth" to **any seventh-less quality** (including maj6/min6) → the fifth; note the intended asymmetry that `seventh` on maj6/min6 falls back to the 6th while `guide7` on maj6/min6 falls back to the fifth (guide tones are a distinct concept). **(c)** the `retrigger` "remainders < 60 ticks are dropped" rule is applied to **every** split segment, not only the trailing remainder — so a note < 120 ticks straddling a chord boundary can split into two sub-60 pieces and emit **zero** notes (the whole note vanishes).
- **Why:** (a)/(b) are dressing-safe gap-fills — dressing (PHASE_4 §6) changes qualities per mood, so a degree must resolve for every quality a pattern might meet, including sus and 6-chords the fallback column doesn't enumerate. (c) treats any sub-60-tick fragment as inaudible regardless of position, consistent with the rule's intent (drop inaudible fragments).
- **Impact:** `src/trackgen/parts/retarget.py`. (c) is a **latent** edge only: the reference banks' shortest retargeted pitched note is the 120-tick 16th pickup (`pr_bs_4`), which can lose ≤ 59 leading ticks at a boundary but never fully vanishes; a future pack authoring a < 120-tick pitched note on a chord boundary would see it disappear. Pinned by `tests/test_foundations.py::test_on_chord_change_retrigger_drops_all_short_segments`. Chunk 3 generators consume these resolutions as-is; a future PHASE_5 §3.3 pass could enumerate the sus/6-chord guide-tone fallbacks and clarify the drop scope explicitly. The `push` tag is emitted even when no boundary falls in the note's span — this is NOT a deviation (§3.3 states flatly "Pushed notes are emitted with tag `push`").
- **Doc amendment:** none applied — these fill unspecified cells / clarify intent rather than change a pinned value. Flagged for a future §3.3 pass.
- **Status:** open

### C-06: Phase-5 pattern-bank rules PT5/PT6/PT7/PT10 are enforced only for packs declaring a Phase-5 marker
- **Date / session:** 2026-07-16, session 06 (Phase 5, chunk 1), T1 loader
- **What deviated:** PHASE_5 §5.5 reads PT10 ("`layeringOrder` present once per pack") and PT6/PT7 ("`mode`/`voicing` required") as **unconditional**, and PT5 (completeness) as applying to any "role with a pattern bank." The loader (`packs/loader.py::_check_pattern_banks`) instead fires PT5/PT6/PT7/PT10 **only when the pack declares at least one Phase-5 marker** (`layeringOrder`, bass `mode`/`walking`, or comping/pads `voicing`). Packs with none — `styles/_stub` (a Phase-1 envelope-violation test fixture) and the reference packs *before T2 authors them* (empty `patterns: []` banks) — load on the legacy Phase-1 flat-envelope path and skip those four whole-bank rules (they still get per-entry PT1/PT2/PT3/PT4/PT8/PT9/PT11).
- **Why:** ~dozens of Phase 1–4 suite tests call `resolve_pack("pop_rock"/"jazz")`, whose pattern banks are empty until T2 (a later task, out of T1's file scope); and the SESSION_06 T1 contract requires keeping `_stub` + all 644 prior tests green. Enforcing the four rules unconditionally would reject those packs at load. `_stub` legitimately has no generation intent, so requiring `layeringOrder`/`voicing` on it is meaningless.
- **Impact:** `src/trackgen/packs/loader.py`. Once T2 authors `pop_rock`/`jazz` with `layeringOrder` + bass `mode` + `voicing` (all present in §7), `phase5=True` and **all four rules fire** on the real reference packs (verified premise: T2's clean-load exercises the enforced path). A pack that authors real patterns but declares **no** marker would escape PT5/PT10 — but it cannot generate (`arrange()` needs `layering_order`, bass gen needs `mode`, comping/pads need `voicing`), so it fails loudly downstream, not silently. A future session (or Phase 8 pack authoring) that wants unconditional enforcement should special-case `_stub` instead of gating on markers. Also latent: PT1's "whole number of bars" is checked against a fixed `_TICKS_PER_BAR = 1920` constant (v1 is 4/4-only per PHASE_1; the envelope model carries no manifest handle).
- **Doc amendment:** none applied — §5.5 does not contemplate the transitional empty-bank state, so this fills an unspecified gap rather than changing a pinned condition. A future PHASE_5 §5.5 pass could state the marker-gating (or exempt `_stub`) explicitly.
- **Status:** open

### C-05: pattern-event authored order need not be non-decreasing in `pos` (PT2)
- **Date / session:** 2026-07-16, session 06 (Phase 5, chunk 1), T1 pattern schema
- **What deviated:** PHASE_5 §5.5 **PT2** reads "events ordered by `pos` **as authored**". T1 first implemented this as a hard *non-decreasing-`pos`* authoring constraint, which the T1 review showed **rejects the normative §7 reference patterns** — they are authored **voice-grouped** (e.g. §7.1 `pr_dr_2a` has pos `0, 960, 480, 1440, 0, 240, …`, decreasing across voices). §7 declares those fixtures "normative golden-test data," and §14/DoD-1 requires the reference packs to load clean, so the strict reading is refuted by the pinned data. PT2 was relaxed to validate only `pos ∈ [0, lengthTicks)`; the authored order is treated as authoritative (generators sort notes `(ticks, midi)` at emit time, §6), not required to be pre-sorted.
- **Why:** golden-value arbitration (ROADMAP §3) — where algorithm/rule text conflicts with the normative worked data, the data wins. "ordered by `pos` as authored" is compatible with (indeed better read as) "the authored `pos` values are authoritative," not "authored events must already be sorted." A non-decreasing constraint would make the normative §7 banks unloadable.
- **Impact:** `src/trackgen/packs/models.py::PatternEnvelope._check_envelope`. Downstream part generators (chunk 3) must not assume authored events are pos-sorted; they sort at emit time (already the pinned §6 behavior). A regression test (`tests/test_patterns_pack.py::test_pt2_voice_grouped_events_load`) loads the literal §7.1 `pr_dr_2a` pos sequence to guard this.
- **Doc amendment:** none needed — the relaxed reading is consistent with §5.5's "as authored" text and required by the normative §7 fixtures; no pinned value changes.
- **Status:** resolved

### C-04: theory voicing API — `voicing_candidates` has no key (quartal reading) and `optimal_voicing_path` gains an additive `anchor` param
- **Date / session:** 2026-07-16, session 04 (Phase 4, chunk 1), T2 voicing
- **What deviated:** The §8.3 pinned signature `voicing_candidates(spec, cls, lane)` carries no key, but §8.4's `quartal` class is defined as "three stacked 4ths **from the scale (§7.4)** starting on a chord tone" — the scale is unresolvable without a key. Implemented as **perfect** fourths from the root (`[0, 5, 10, 15]`, four voices), the only key-free reading. Separately, §8.6's `optimal_voicing_path` drift term needs the lane anchor, absent from the pinned signature; implemented as an **additive keyword-only** `anchor: int | None = None` (default derives the candidate-range midpoint, recovering the lane midpoint when candidates fill the lane), so the pinned positional signature is preserved and Phase 5 injects the real anchor.
- **Why:** the §8.3 signatures and the §8.4/§8.6 prose are mutually under-specified on the key/anchor; both readings are the minimal key-free / additive resolutions. No golden in this chunk exercises quartal (its voicing goldens land in PHASE_5 §13.6), so nothing is pinned against these choices yet.
- **Impact:** `src/trackgen/theory/voicing.py`. Phase 5 owns candidate-class-per-role policy and the quartal/fifths voicing goldens (PHASE_5 §13.6) — that session should confirm the perfect-4th quartal reading (or widen the signature to pass a key/scale) and pass the real lane anchor. Also latent: `rootless_a`/`rootless_b`/`drop2` on **triads** degrade to fewer voices than their 4-note formulas imply (deterministic; the DP pads mixed cardinality) — not pinned; Phase 5 policy decides class-per-role so triads never hit seventh-chord classes.
- **Doc amendment:** none applied (deferred to the PHASE_5 §13.6 decision; both readings documented in the `voicing.py` module docstring). Additive/under-specification resolutions, not a change to any pinned value.
- **Status:** open

### C-03: P8 admits the tritone-substitute dominant (bII7), beyond the literal §3.2 "D-function"
- **Date / session:** 2026-07-16, session 04 (Phase 4), T4 progressions loader
- **What deviated:** PHASE_4 §4.3 **P8** pins "turnarounds … final chord D-function" and §14 DoD-1 requires the §9.2 reference pack to **load clean**. These two pins conflict: §9.2's `tritone_turn` ends on `bII7`, but the §3.2 function table maps degree `b2 → S`, so a literal `chord_function(last) == "D"` check rejects the reference pack. The loader implements P8 as "final chord is dominant-functioning" = `chord_function == "D"` **OR** a dominant-seventh rooted on `b2` (the SubV / tritone substitution, which resolves to I exactly as V does).
- **Why:** the verbatim-reference-loads-clean requirement (D-S4 discipline + DoD-1) is the binding tie-breaker; `bII7` is functionally the dominant in a turnaround relaunch (it is the corpus-standard tritone sub), and the §3.2 table's generic `b2 → S` does not model the substitution context. The narrow admission (dom7-family rooted on b2 only) keeps P8 otherwise strict — it still rejects a turnaround ending on a tonic or plain subdominant (tested).
- **Impact:** `src/trackgen/packs/models.py::_relaunches_as_dominant` carries the reconciliation and a pointer to this caveat. It admits any dom7-family chord **rooted on pitch-class 1** (i.e. `bII7` or its enharmonic `#I7`) — the SubV is a pitch-defined function, so the pc test is intentionally slightly broader than the "b2 spelling" prose. Any Phase 8 pack authoring a turnaround that ends on a non-dominant, non-SubV chord will still be rejected. If a future function-table revision assigns `b2 → D` for tritone subs, this special case becomes redundant and can fold back into the plain `chord_function == "D"` check. The runtime turnaround transform (§5.4, Phase 4 harmony stage — not built in T4) should use the same "dominant-functioning relaunch" notion when it validates/consumes turnarounds, not the raw §3.2 label.
- **Doc amendment:** none applied (design text left as pinned; flagged for reviewer). A future PHASE_4 §4.3 pass should either (a) reword P8 to "dominant-functioning (D-function or SubV)", or (b) extend the §3.2 table's b2 row — either makes the doc self-consistent.
- **Status:** open

### C-02: the degradation ladder (§7.3) is unreachable under the pinned §5.2 + §7.1 rules
- **Date / session:** 2026-07-15, session 03 (Phase 3)
- **What deviated:** PHASE_3 §7.1 step 5 / §7.3 present the `degrade` ladder as reachable ("exists for budgets too small for the template's drawn/minimal configuration"), and DoD §11.7 asks for "a fixture exercising each degrade op class." In the faithful implementation the ladder is **provably unreachable through `form()`**: §5.2 gates a template *in* only if `minBars ≤ barBudget` (its all-smallest config fits); §7.1 step-3 resolves each bar count only to options keeping `minimalTotal ≤ barBudget`, and the smallest option never raises `minimalTotal`, so the "0 feasible → take smallest" branch never fires and `minimalTotal ≤ barBudget` holds throughout; the arithmetic repeat count then yields `total ≤ barBudget` even when clamped up to `count.min` (that case gives `total == minimalTotal`). So the step-5 loop guard `total > barBudget` is never true for a *selected* template; the only over-budget path (no template eligible) routes to the step-6 **fallback**, not the ladder. Confirmed empirically: 0 ladder ops across ~40k property-matrix runs, and two independent review agents reconstructed the proof.
- **Why:** the pinned eligibility filter (§5.2, D4) and the pinned feasibility filter (§7.1 step 3b, D13) together guarantee fit before the ladder can ever run — the ladder and the eligibility/feasibility gates are two mechanisms solving the same "make it fit" problem, and the gates always win first. The step-3b "0 feasible" case the ladder was meant to repair is itself unreachable because the smallest authored option is always feasible.
- **Impact:** the ladder code (`src/trackgen/form/stage.py`, the step-5 branch) is retained as **defensive/unreachable** and is correct if ever reached (drop/shrink/dropFromRepeat verified by inspection). DoD §11.7's "exercise each degrade op class" was satisfied via a **substitute**: `test_degrade_ladder_authored_order` asserts each reference pack's authored ladder covers all three op classes in D11 order (data/config level); `test_30s_at_slow_tempo_valid_form` + tiny-budget fallback tests cover the fallback; a full-grid regression guard asserts the ladder never fires and the hard ceiling always holds. A future change that could make the ladder live — e.g. loosening §5.2 eligibility, or a pack/rule that lets an over-budget template be *selected* — must add real ladder-execution coverage. Two latent, currently-moot validation gaps in the ladder's own input rules were left unfixed for the same reason (they guard the dead path): F8's ending-candidate set omits the section a `drop` op newly exposes as final, and F9 accepts a top-level `drop:` targeting a repeat-only type (a silent no-op at runtime). Revisit both if Phase 8 authoring ever makes the ladder reachable.
- **Doc amendment:** PHASE_3 §7.3 amended (post-review, 2026-07-15) with an "Implementation note (v1, defensive/unreachable)" paragraph documenting the eligibility+feasibility proof and the white-box substitute for §11.7. Not an algorithm change — the fitter's behavior is unaffected.
- **Resolution (post-review, 2026-07-15):** user signed off on option A — keep the ladder as defensive code. The step-4/5 logic was extracted to a module-level `_fit_and_degrade` (`src/trackgen/form/stage.py`) and its drop/shrink/dropFromRepeat op semantics + authored-order/exhaustion control flow are now locked by direct white-box unit tests (`tests/test_form.py::test_ladder_*`), converting §11.7's "verified by inspection" into executable coverage. The two latent F8/F9 input-validation gaps remain intentionally unfixed (they guard the dead path); revisit only if Phase 8 makes the ladder reachable.
- **Status:** resolved

### C-01: `PARAM_MALFORMED` structural error code added beyond the §3.1 catalog
- **Date / session:** 2026-07-15, session 02 (Phase 2)
- **What deviated:** PHASE_2 §3.1 pins a 14-code validation catalog (all semantic conditions, assuming well-typed JSON input). The implementation adds a 15th code, `PARAM_MALFORMED`, emitted by `generate_plan` when `Params.model_validate` rejects a malformed field *type* (e.g. a fractional `tempoBpm`, a non-mapping `key`/`roleFlavors`). `validate_params` (the §3.1 catalog function) is unchanged and still returns only the 14 documented codes.
- **Why:** `validate_params` operates on the raw client dict and deliberately defers type/structural checks to the pydantic `Params` model (D-S6 two-layer design). Without wrapping, a malformed-type request escaped the public `generate_plan` boundary as a raw `pydantic.ValidationError` — contradicting §3.1's "failures return the full list of errors." Wrapping into `ParamsInvalid` with a structural code keeps a single structured error type at the boundary without fabricating a *semantic* §3.1 code.
- **Impact:** A later client-contract/HTTP layer enumerating error codes must include `PARAM_MALFORMED` (structural) alongside the 14 semantic §3.1 codes. Its `field` is a pydantic dotted location (e.g. `tempoBpm`), and its `message` is the pydantic message (not a hand-authored catalog message). Purely additive — no existing code changes meaning.
- **Doc amendment:** none needed — §3.1 does not specify behavior for malformed input types, so this fills an unspecified gap rather than changing a pinned condition. A future PHASE_2 §3.1 pass could document it explicitly.
- **Status:** resolved
