# Caveats — Deviations from the Pinned Design

The design docs (`ROADMAP.md`, `PHASE_1.md`–`PHASE_8.md`) are binding, but implementation will occasionally force a deviation. Every deviation is logged here so its impact stays visible to later sessions, which otherwise have no memory of it.

**Log an entry when:** a pinned contract/algorithm/data format is changed or reinterpreted; a printed worked-example sample is found wrong (golden-value arbitration rule 2, `ROADMAP.md` §3); an algorithm ambiguity is resolved; scope is moved between phases/sessions; a dependency pin forces a design adjustment.

**Not caveats:** bugs fixed in this project's own new code, refactors that don't change pinned contracts, or decisions the PHASE docs explicitly left open (those are just decisions — record them in the session plan and PROGRESS.md).

## Entry format

```
### C-<nn>: <one-line title>
- **Date / session:** YYYY-MM-DD, session NN (Phase N)
- **What deviated:** the pinned text vs. what was actually built
- **Why:** the concrete forcing reason
- **Impact:** downstream PHASE docs / phases / fixtures affected; what a later session must know
- **Doc amendment:** commit hash of the PHASE/ROADMAP amendment, or "none needed" with justification
- **Status:** open | resolved
```

Numbered sequentially (`C-01`, `C-02`, …), never renumbered. If a later session resolves or supersedes an entry, update its **Status** in place and note how — do not delete entries.

### C-11: drum notes carry internal voice/`ornament` provenance tags beyond the §3.9 four (the mutation pass needs provenance the `PhraseNote` IR lacks)
- **Date / session:** 2026-07-17, session 10 (Phase 6, chunk 1), T3 mutation + whole-chunk review
- **What deviated:** PHASE_6 §3.9 lists the tags stage 6 *contributes to output* as exactly `"fill"`, `"crash"`, `"var"`, `"hold"`. But two §3.7 mutation operators need drum-voice/ornament provenance that the pinned `PhraseNote` IR (PHASE_1 §4.5: `ticks`/`durationTicks`/`midi`/`velocity`/`tags`) does not carry: **`hat_lift`** must find `hat_closed` specifically (both `hat_closed` and `hat_open` collapse to the single `"hats"` voice-track via `generators._VOICE_TRACK`), and **`drop_ornament`** must find `minDensity` events (consumed at instantiation, §3.5). No Phase-5 phrase golden broke (they use tag-membership checks, not `tags == []`). A later phase reading a drum `PhraseNote.tags` must know drum notes now carry a voice tag (+ maybe `"ornament"`) as their first entries. A future PHASE_6 §3.9 / §4.5 pass could state the internal-provenance-tag convention explicitly (or the IR could gain a `voice` field).
- **Doc amendment:** none applied — §3.9 governs *contributed output* tags and these are internal/serialize-dropped, so this fills an unspecified integration gap rather than changing a pinned value. Flagged for a future §3.9/§4.5 clarification.

### C-10: the thin Serializer does not de-duplicate coincident same-voice drum triggers (latent V3 edge)
- **Date / session:** 2026-07-17, session 09 (Phase 5, chunk 4), whole-phase correctness review
- **What deviated:** PHASE_5 §8.3 pins the Serializer as *thin* — concatenate a track's Phrases, sort `(ticks, midi)`, clamp/truncate — and is silent on de-duplication. Neither the Serializer (`pipeline/serialize.py`) nor the drum generator (`parts/generators.py::_generate_drums`) nor a loader PT-rule forbids two drum events at the **same `pos`** mapping to one track. For a **NoiseSynth**-backed drum track (the snare in the reference kit) that produces two `NoteEvent`s at one tick, which trips validator **V3** ("duplicate ticks (double-hit)", `schema/validate.py`). Resolved reading: the thin Serializer trusts non-colliding drum authoring; coincident same-voice de-dup is **not** performed in v1.
- **Why:** §8.3's "thin" intent + the reference banks avoiding the collision purely by **authoring convention** (e.g. `pr_dr_3` deliberately omits a 4& `hat_closed` that would coincide with its `hat_open`). A 720-document fuzz (both packs × 6 moods × 5 lengths × 12 seeds) produced **zero** V-rule violations, so the edge is unreachable through `generate_track` in v1 — adding a de-dup or a loader PT-check at the milestone close-out would be unpinned surface for no reachable benefit.
- **Impact:** `pipeline/serialize.py` / `parts/generators.py`. **Latent only.** A future/degenerate drum pattern authoring two same-voice hits at one `pos`, or a pack backing the shared `hats` track (closed+open at one `pos`) with a NoiseSynth patch instead of MetalSynth, would serialize a V3-invalid document. Closing it is a one-line coincident-tick de-dup in the drum-track builder, or a loader PT-rule forbidding coincident same-voice drum events — a natural Phase-6 item (Phase 6 authors fills/variation in `parts/` and can add the guard where it edits). - **Doc amendment:** none applied — §8.3 does not contemplate de-dup, so this resolves an unspecified point rather than changing a pinned value. A future PHASE_5 §8.3 / §5.5 pass could state the no-coincident-same-voice-drum-event convention (or add the PT-check) explicitly.

### C-07: §3.3 retargeting — three under-specified points resolved (guide3-over-sus, guide7 fallback scope, <60-tick drop on all retrigger segments)

- **What deviated:** PHASE_5 §3.3's degree table + `onChordChange` prose left three points under-specified; `parts/retarget.py` resolves them as: **(a)** `guide3` over a **suspended** chord (which has no guide third) → the `third` slot (the suspension tone); §3.3's `guide3` fallback cell is "—", implicitly assuming a third always exists. **(b)** `guide7` fallback broadened from the literal "triads → the fifth" to **any seventh-less quality** (including maj6/min6) → the fifth; note the intended asymmetry that `seventh` on maj6/min6 falls back to the 6th while `guide7` on maj6/min6 falls back to the fifth (guide tones are a distinct concept). **(c)** the `retrigger` "remainders < 60 ticks are dropped" rule is applied to **every** split segment, not only the trailing remainder — so a note < 120 ticks straddling a chord boundary can split into two sub-60 pieces and emit **zero** notes (the whole note vanishes).

The implementation adds a 15th code, `PARAM_MALFORMED`, emitted by `generate_plan` when `Params.model_validate` rejects a malformed field *type* (e.g. a fractional `tempoBpm`, a non-mapping `key`/`roleFlavors`). `validate_params` (the §3.1 catalog function) is unchanged and still returns only the 14 documented codes.
- **Why:** `validate_params` operates on the raw client dict and deliberately defers type/structural checks to the pydantic `Params` model (D-S6 two-layer design). Without wrapping, a malformed-type request escaped the public `generate_plan` boundary as a raw `pydantic.ValidationError` — contradicting §3.1's "failures return the full list of errors." Wrapping into `ParamsInvalid` with a structural code keeps a single structured error type at the boundary without fabricating a *semantic* §3.1 code.
- **Impact:** A later client-contract/HTTP layer enumerating error codes must include `PARAM_MALFORMED` (structural) alongside the 14 semantic §3.1 codes. Its `field` is a pydantic dotted location (e.g. `tempoBpm`), and its `message` is the pydantic message (not a hand-authored catalog message). Purely additive — no existing code changes meaning.
- **Doc amendment:** none needed — §3.1 does not specify behavior for malformed input types, so this fills an unspecified gap rather than changing a pinned condition. A future PHASE_2 §3.1 pass could document it explicitly.
